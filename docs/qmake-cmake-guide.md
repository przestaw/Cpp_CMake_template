## 1. Staged Separation Strategy

Changing the build system, upgrading the C++ standard, and porting from Qt 5 to Qt 6 simultaneously tangles compiler errors, linker ABI mismatches, and macro regressions. Split the migration into three independent, verifiable stages:

| Stage | Baseline | Candidate | Acceptance Question |
| :--- | :--- | :--- | :--- |
| **1. Build-system parity** | `qmake` + Qt 5.15 + C++17 | `CMake 3.25+` + same Qt 5.15, compiler, arch, and C++17 | Do compile flags, defines, generated headers, links, and install trees match? |
| **2. C++ standard upgrade** | Verified CMake C++17 build | Same CMake + Qt, switched to C++20 | Which project sources or third-party public headers break under C++20 rules? |
| **3. Qt 5.15 → Qt 6 port** | Verified CMake Qt 5.15 build (`QT_DISABLE_DEPRECATED_BEFORE=0x050F00`) | Same CMake build switched to Qt 6 (`Qt6::*` / `qt_add_*`) | Which removed Qt 5 APIs, modules, QML imports, or runtime plugins require updates? |

> **Toolchain coupling:** When a target Qt 6 release requires a newer compiler or C++17/C++20 floor than the legacy Qt 5 toolchain, record that prerequisite explicitly as its own step rather than diagnosing C++ dialect breaks as CMake generation bugs.

### Handling Legacy Third-Party Headers During a C++20 Upgrade

Upgrading from C++17 to C++20 removes deprecated standard-library typedefs such as `std::allocator<T>::pointer`, which can break public headers of prebuilt dependencies:

```cpp
// Pre-C++20 spelling (removed in C++20):
using pointer = typename std::allocator<T>::pointer;

// C++17 / C++20 compatible spelling (#include <memory>):
using pointer = typename std::allocator_traits<std::allocator<T>>::pointer;
```

Prefer upgrading the dependency package first. When a vendor package must stay pinned temporarily, place a narrowly scoped compatibility header in the build tree (see [`../examples/qmake-migration/snippets/allocator-header-example.h`](../examples/qmake-migration/snippets/allocator-header-example.h)):

- hash-check the exact installed vendor header at configure time so package upgrades fail fast instead of silently shadowed,
- prepend the overlay directory `PRIVATE` (or targeted `BEFORE`) only on the internal targets that include it,
- remove the overlay as soon as the upstream dependency is updated.

## 2. Reference `before` / `after` Slice (`examples/qmake-migration/`)

Start any repository migration by hand-porting one small vertical slice: a shared library (`democore`) with a `Q_OBJECT` class, an exported namespace enum (`Q_NAMESPACE_EXPORT`), a build-time schema code generator, and a consumer executable (`demo`). Full buildable files live in [`../examples/qmake-migration/`](../examples/qmake-migration/README.md).

### Subdirectory Ordering vs Target Link Graph

`qmake` orders directories in `SUBDIRS` and repeats raw `-L`/`-l` flags in the consumer; CMake expresses build order, symbol linking, and usage requirements in a single `target_link_libraries()` edge:

```qmake
# before/demo.pro
TEMPLATE = subdirs
SUBDIRS += core app
app.depends = core

# before/app/app.pro
INCLUDEPATH += $$PWD/../../common/include
LIBS += -L$$OUT_PWD/../bin -ldemocore
```

```cmake
# after/CMakeLists.txt
add_library(democore SHARED
    "${common}/src/counter.cpp"
    "${common}/include/demo/counter.h"
    "${common}/include/demo/core_export.h"
    "${generated}"
)
target_include_directories(democore
    PUBLIC "$<BUILD_INTERFACE:${common}/include>"
    PRIVATE "${CMAKE_CURRENT_BINARY_DIR}/generated"
)

add_executable(demo "${common}/src/main.cpp")
target_link_libraries(demo PRIVATE democore)
```

Note that `add_dependencies(demo democore)` only orders target builds; it does not link libraries or propagate `PUBLIC` include directories.

### Implicit `.prf` Features vs Explicit Target Properties

`before/settings.pri` loads `before/features/demo_rules.prf` via `QMAKEFEATURES`, injecting `DEFINES += DEMO_FEATURE_LOADED`. In CMake, avoid hidden environment-driven feature files and attach required definitions explicitly to targets (or to a shared project helper function):

```cmake
target_compile_definitions(democore PRIVATE DEMO_CORE_BUILD DEMO_FEATURE_LOADED)
target_compile_definitions(demo PRIVATE DEMO_FEATURE_LOADED)
```

## 3. Evaluating the qmake Model (`qmig export` & `diff_models.py`)

`.pro` files evaluate platform scopes (`win32`, `unix:!macx`), `.pri` includes, `.prf` features, `$$system()`, and `exists()` checks dynamically. Never parse `.pro` files with regular expressions — let `qmake` evaluate its own language and export the effective state via [`../tools/qmake-migration-kit/features/migration_export.prf`](../tools/qmake-migration-kit/features/migration_export.prf) (`CONFIG+=migration_export`).

```sh
python3 tools/qmake-migration-kit/export_model.py \
  --source-dir tools/qmake-migration-kit/examples/demo \
  --features tools/qmake-migration-kit/examples/demo/features \
  --profile linux-qt5-release \
  --output out/demo-release.json --qmake-arg CONFIG+=release demo.pro

python3 tools/qmake-migration-kit/export_model.py \
  --source-dir tools/qmake-migration-kit/examples/demo \
  --features tools/qmake-migration-kit/examples/demo/features \
  --profile linux-qt5-debug \
  --output out/demo-debug.json --qmake-arg CONFIG+=debug demo.pro

python3 tools/qmake-migration-kit/diff_models.py \
  out/demo-release.json out/demo-debug.json --summary
```

Key operational rules for model export:

- **Native host evaluation:** Exporting `-spec win32-msvc` on Linux helps inspect project topology, but `exists()`, registry/SDK lookups, and toolset mkspecs behave differently on real Windows builders. Always export and capture Windows profiles inside a native x64 MSVC environment.
- **`debug_and_release` multi-pass (`schemaVersion: 2`):** MSVC mkspecs enable `CONFIG += debug_and_release` by default, evaluating each `.pro` three times (top-level + `debug` + `release` build passes). Select one pass explicitly with `--variant release` or `--variant debug` in `diff_models.py` and `map_to_cmake.py`, or set `CONFIG -= debug_and_release` in single-variant capture profiles.
- **Export vs actual command lines:** `.prf` probes observe `qmake` state at feature-evaluation time; later mkspec/Makefile generators still append flags (for example `designer_defines.prf` or default release flags). Treat `export` as the structural model and `qmig capture` (`buildtree.json`) as ground truth for compiler/linker invocations.

## 4. Compiler Flags, Quoting, DLL Boundaries & Link Semantics

### DLL Producer vs Consumer Macro Ownership (`PRIVATE`)

In a Windows shared library, the macro that selects `__declspec(dllexport)` (`Q_DECL_EXPORT`) belongs exclusively to the library target being built. Propagating it as `PUBLIC` forces downstream consumers to see `__declspec(dllexport)` instead of `__declspec(dllimport)` (`Q_DECL_IMPORT`), causing unresolved `staticMetaObject` and vtable linker errors:

```qmake
# qmake: core/core.pro defines DEMO_CORE_BUILD; app/app.pro does NOT
DEFINES += DEMO_CORE_BUILD
```

```cmake
# WRONG — leaks Q_DECL_EXPORT to every consumer:
# target_compile_definitions(democore PUBLIC DEMO_CORE_BUILD)

# CORRECT — producer exports, consumers import:
target_compile_definitions(democore PRIVATE DEMO_CORE_BUILD)
target_link_libraries(demo PRIVATE democore)
```

### Qt Designer `CONFIG += plugin` vs Install Directory Helpers

Qt's `designer_defines.prf` defines `QDESIGNER_EXPORT_WIDGETS` only when a target sets `CONFIG += plugin`:

```qmake
TEMPLATE = lib
CONFIG += plugin designer   # -> defines QDESIGNER_EXPORT_WIDGETS
```

If a codebase installs an ordinary shared widget library into the same staging folder as Designer plugins via a custom `.pri` install helper, do **not** infer `QDESIGNER_EXPORT_WIDGETS` or `add_library(... MODULE)` from the install path. Model three independent properties per target:

1. **Linkable target kind:** `SHARED` (produces a `.lib` import library for downstream C++ linkers) vs `MODULE` (runtime-loaded plugin only).
2. **Export macro ownership:** `PRIVATE` producer macro per shared library; `QDESIGNER_EXPORT_WIDGETS` only on actual Designer plugin targets.
3. **Install destination:** `RUNTIME DESTINATION bin` + `ARCHIVE DESTINATION lib` for shared libraries vs plugin subdirectories for `QPluginLoader`.

### `Release` `NDEBUG` Parity & Target-Scoped `/permissive-`

- **`NDEBUG` in Release builds:** CMake adds `-DNDEBUG` / `/DNDEBUG` automatically in `Release`, `RelWithDebInfo`, and `MinSizeRel`, whereas `qmake` `CONFIG += release` only defines `QT_NO_DEBUG` and leaves standard C `<cassert>` `assert()` active. Decide explicitly per product whether to adopt CMake's standard `NDEBUG` behavior (recording it in `policy.json`) or preserve `assert()` parity on legacy targets:

```cmake
if(MSVC)
    target_compile_options(legacy_component PRIVATE "$<$<CONFIG:Release>:/UNDEBUG>")
else()
    target_compile_options(legacy_component PRIVATE "$<$<CONFIG:Release>:-UNDEBUG>")
endif()
```

- **Target-local MSVC conformance (`/permissive-`):** Dropping `/permissive-` from a `.pro` target breaks C++ headers that rely on standard ISO operator tokens (`not`, `and`, `or`, common in Boost or vendor SDKs). Keep `/permissive-` `PRIVATE` and restricted to `CXX` on the targets that require it (see [`../examples/qmake-migration/snippets/target-options.cmake`](../examples/qmake-migration/snippets/target-options.cmake)):

```cmake
target_compile_options(legacy_component PRIVATE
    "$<$<COMPILE_LANG_AND_ID:CXX,MSVC>:/permissive->"
)
```

### Structured Quoting, `SHELL:` Option Grouping & MSVC Response Files

Compiler defines and options pass through distinct escaping layers in `qmake` (raw Makefile text) vs CMake (structured argv / Ninja / MSVC `.rsp` response files):

- **String-literal defines:** Strip one level of shell quoting when moving from `qmake` to `target_compile_definitions`:

```qmake
# qmake
DEFINES += APP_LABEL=\\\"demo\\\"
```

```cmake
# CMake
target_compile_definitions(demo PRIVATE APP_LABEL="demo")
```

- **Repeated paired options (`SHELL:`):** CMake deduplicates repeated tokens such as `-include a.h -include b.h` into `-include a.h b.h` unless grouped with `SHELL:` (supported on GCC/Clang options):

```cmake
target_compile_options(component PRIVATE
    "SHELL:-include \"${CMAKE_CURRENT_SOURCE_DIR}/compat/first.h\""
    "SHELL:-include \"${CMAKE_CURRENT_SOURCE_DIR}/compat/second.h\""
)
```

- **Multi-word Windows linker flags & `/Fo`:** Keep multi-argument or quoted MSVC linker switches such as `/MANIFESTDEPENDENCY:"type='win32' ..."` intact as single option values so response-file splitting never turns trailing tokens into bogus `.obj` inputs. When parsing custom `cl.exe` commands, handle all documented `/Fo` forms (`/Fofile.obj`, `/Fodir/`, and `/Fo: file.obj`).

### `IMPORTED` Targets, `PkgConfig::`, Link Order & `VERSION` / `SOVERSION`

Replace raw `-L/path -lfoo` flags with `IMPORTED` targets that carry headers, definitions, and per-configuration binaries:

- **Windows shared `IMPORTED` libraries:** Always specify both `IMPORTED_LOCATION_<CONFIG>` (`.dll`) and `IMPORTED_IMPLIB_<CONFIG>` (`.lib`), plus `MAP_IMPORTED_CONFIG_RELWITHDEBINFO` when the vendor SDK ships only `Debug` and `Release` variants (see [`../examples/qmake-migration/snippets/windows-imported-library.cmake`](../examples/qmake-migration/snippets/windows-imported-library.cmake)):

```cmake
add_library(Vendor::Transport SHARED IMPORTED)
set_target_properties(Vendor::Transport PROPERTIES
    IMPORTED_CONFIGURATIONS "DEBUG;RELEASE"
    IMPORTED_LOCATION_RELEASE "${TRANSPORT_ROOT}/bin/transport.dll"
    IMPORTED_IMPLIB_RELEASE "${TRANSPORT_ROOT}/lib/transport.lib"
    IMPORTED_LOCATION_DEBUG "${TRANSPORT_ROOT}/bin/transportd.dll"
    IMPORTED_IMPLIB_DEBUG "${TRANSPORT_ROOT}/lib/transportd.lib"
    MAP_IMPORTED_CONFIG_RELWITHDEBINFO Release
    INTERFACE_INCLUDE_DIRECTORIES "${TRANSPORT_ROOT}/include"
)
target_link_libraries(network_component PRIVATE Vendor::Transport)
```

- **`PkgConfig::` imported targets:** When a library ships `.pc` metadata (e.g. `xmlsec1`), consume `pkg_check_modules(... IMPORTED_TARGET)` rather than hard-coding one Linux distribution's `-D` flags across platforms (see [`../examples/qmake-migration/snippets/dependency-metadata.cmake`](../examples/qmake-migration/snippets/dependency-metadata.cmake)).
- **Static archive link order:** Unix linkers resolve static archives left-to-right, and `--as-needed` drops unused shared libraries. Declare direct `target_link_libraries()` edges on every consumer, and use `$<LINK_GROUP:RESCAN,a,b>` (CMake 3.24+) only for genuine circular static-library dependencies.
- **Shared-library `VERSION` and `SOVERSION`:** `qmake` sets `.so.<major>.<minor>.<patch>` symlinks by default when `VERSION` is defined, whereas CMake leaves shared libraries unversioned unless `VERSION` and `SOVERSION` properties are set explicitly (see [`../examples/qmake-migration/snippets/install-versioning.cmake`](../examples/qmake-migration/snippets/install-versioning.cmake)).

## 5. Qt Code Generation: `AUTOMOC`, `AUTOUIC`, `AUTORCC`, Custom Generators & QML

### Source vs Shadow-Build Paths & `AUTOMOC` Header Discovery

`qmake` implicitly adds both the `.pro` source directory (`$$PWD`) and the shadow-build directory (`$$OUT_PWD`) to include paths unless `CONFIG += no_include_pwd` is set. Make required source and generated binary include directories explicit on each CMake target, and follow strict `AUTOMOC` rules:

1. **List meta-object headers in `target_sources()`:** Do not rely on `AUTOMOC` guessing header paths from `.cpp` basenames alone — list headers declaring `Q_OBJECT`, `Q_GADGET`, or `Q_NAMESPACE` explicitly in `add_library()` / `target_sources()`.
2. **Keep `Q_NAMESPACE` / `Q_NAMESPACE_EXPORT` on its own line:**

```cpp
namespace Demo {
Q_NAMESPACE_EXPORT(DEMO_CORE_EXPORT)   // standalone line for reliable AUTOMOC scanning
enum class Mode { Normal, Fast };
Q_ENUM_NS(Mode)
} // namespace Demo
```

3. **Fix mismatched `#ifndef` / `#define` header guards:** CMake compiles per-target moc outputs together inside `mocs_compilation.cpp`, which immediately surfaces typos in header include guards or duplicate `Q_DECLARE_METATYPE` registrations that survived isolated compilation under `qmake`.
4. **Preserve `#include "foo.moc"` without double moc rules:** When a `.cpp` file defines a private `Q_OBJECT` helper class and ends with `#include "foo.moc"`, let `AUTOMOC` own generation — never add a manual `qt_wrap_cpp()` rule for the same file.
5. **Narrow `SKIP_AUTOMOC` for false positives:** If a source file contains `Q_OBJECT` inside a comment/string literal and triggers a spurious moc scan, disable `AUTOMOC` on that single file rather than the whole target:

```cmake
set_property(SOURCE src/doc_snippet.cpp PROPERTY SKIP_AUTOMOC ON)
```

### `AUTOUIC_SEARCH_PATHS`, Public `ui_*.h` Contracts & Colliding UIC Guards

- **`AUTOUIC_SEARCH_PATHS`:** When `#include "ui_editor.h"` refers to `.ui` files stored in subdirectories or generated into the build tree, set `AUTOUIC_SEARCH_PATHS` explicitly on the target (keeping already-absolute paths unprefixed):

```cmake
set_property(TARGET panel PROPERTY AUTOUIC_SEARCH_PATHS
    "${CMAKE_CURRENT_SOURCE_DIR}/forms"
    "${CMAKE_CURRENT_BINARY_DIR}/generated/forms"
)
target_sources(panel PRIVATE forms/editor.ui)
```

- **Legacy public headers including `ui_*.h`:** Ideally, forward-declare `namespace Ui { class Editor; }` in public headers and include `ui_editor.h` in `.cpp` only. If an existing public API header includes `ui_*.h` directly during Stage 1 parity, note that single-config generators write `<target>_autogen/include` while multi-config generators write `<target>_autogen/include_$<CONFIG>` — expose the generator-expression path only while refactoring is deferred, and never export raw build-tree paths into installed `Config.cmake` targets.
- **Colliding UIC header guards on dotted `.ui` filenames:** In Qt 5.15, `uic` derives its `#ifndef` guard by truncating at the first dot:

| Input `.ui` | Generated header | Guard emitted by Qt 5.15 `uic` |
| :--- | :--- | :--- |
| `panel.alpha.ui` | `ui_panel.alpha.h` | `UI_PANEL_H` **(collision)** |
| `panel.beta.ui` | `ui_panel.beta.h` | `UI_PANEL_H` **(collision)** |
| `panel.alpha.ui` | `ui_alpha_panel.h` | `UI_ALPHA_PANEL_H` |
| `panel.beta.ui` | `ui_beta_panel.h` | `UI_BETA_PANEL_H` |

See [`../examples/qmake-migration/uic-guard-case/README.md`](../examples/qmake-migration/uic-guard-case/README.md) for the runnable reproduction. Rename dotted form outputs to underscores (`ui_alpha_panel.h`) rather than applying `AUTOUIC_OPTIONS "-p"` globally across targets.

### Custom Code Generators, `AUTOGEN_TARGET_DEPENDS` & `QT_PLUGIN_PATH`

When a build-time tool generates C++ sources, `Q_OBJECT` headers, and `.ui` forms, enforce the full dependency chain:

```text
host generator + runtime DLLs / Designer plugins
  -> generated .cpp / .h / .ui (single-owned OUTPUT list)
  -> <target>_autogen (MOC / UIC via AUTOGEN_TARGET_DEPENDS)
  -> C++ compilation -> linking
```

Key rules (full template in [`../examples/qmake-migration/snippets/generated-forms-ordering.cmake`](../examples/qmake-migration/snippets/generated-forms-ordering.cmake)):

- **Explicit `OUTPUT` vs `BYPRODUCTS`:** List every generated `.h`, `.cpp`, and `.ui` file consumed by compilation in `OUTPUT` (Makefiles generators do not rebuild missing `BYPRODUCTS` on demand). Never allow two parallel `add_custom_command()` calls to write the same shared header.
- **Order before `AUTOMOC` / `AUTOUIC`:** Connect a custom target (`add_custom_target(panel_forms DEPENDS ${outputs})`) to `AUTOGEN_TARGET_DEPENDS` so `moc` and `uic` never start before generated inputs exist.
- **Process-local `QT_PLUGIN_PATH` for build-time tools:** If a form generator loads custom Qt Designer widget plugins at build time, depend on the plugin targets and inject `QT_PLUGIN_PATH` for that command process only via `${CMAKE_COMMAND} -E env`:

```cmake
add_custom_command(
    OUTPUT ${outputs}
    COMMAND "${CMAKE_COMMAND}" -E make_directory "${form_dir}"
    COMMAND "${CMAKE_COMMAND}" -E env
        "QT_PLUGIN_PATH=${CMAKE_BINARY_DIR}/tool-plugins"
        "$<TARGET_FILE:form_generator>" "${schema}" "${form_dir}"
    DEPENDS form_generator designer_widgets "${schema}"
    VERBATIM
)
```

- **Smoke-test compiled generators early:** On Windows, a compiled host tool that exits before `main()` (e.g. `0xC0000135` `STATUS_DLL_NOT_FOUND`) indicates missing runtime DLLs on `PATH`, not a schema syntax error. Run `<tool> --help` or a one-line smoke generation step before launching large parallel builds.

### `.qrc` Resources (`AUTORCC`) vs `install()` Assets & QML Checklist

- **`.qrc` vs filesystem install:** Adding a `.qrc` file to `target_sources()` embeds assets under `qrc:/...` via `AUTORCC`; it does **not** copy loose files into the install prefix. Conversely, `install(FILES ...)` stages files on disk without registering `qrc:/` resources. Verify both mechanisms against your packager's expected file globs.
- **QML module migration checklist:** Simply linking `Qt5::Qml` / `Qt6::Qml` does not validate QML runtime loading. Verify:
  1. Module URI, version numbers, `qmldir`, and `.qmltypes` metadata.
  2. Resource prefixes and `qrc:/` URLs loaded by `QQmlApplicationEngine`.
  3. Backing C++ plugin targets and `QML_IMPORT_PATH` / staged plugin directories.
  4. Ahead-of-time cache generation (`qmlcachegen`) and a headless startup smoke test run from the staged install directory.
  5. After moving to Qt 6, consolidate `.qml` files, C++ backing types, and resource prefixes into `qt_add_qml_module()` (`qt_standard_project_setup(REQUIRES 6.5)` sets modern `QTP0001` / `QTP0004` resource policies).

## 6. Four Levels of Verification ("Green")

Treat migration completion as four progressive gates (summarized in [`../examples/qmake-migration/parity-checklist.csv`](../examples/qmake-migration/parity-checklist.csv)):

1. **Configure & generation:** Verify selected Qt version, compiler, architecture, and dependency paths in `CMakeCache.txt` and CMake File API replies. For multi-config generators, select the matching configuration by name in File API and pass `--config <cfg>` consistently. Ensure the host Ninja version supports CMake's `AUTOMOC` depslog format (Ninja ≥ 1.10; older Ninja 1.8 fails with `multiple outputs aren't supported by depslog`).
2. **Compile & link parity:** Match translation units by `(source, artifact)` rather than filename alone, preserving include directory order and macro quoting. Ensure capture completeness gates reject empty compile captures (`capture.empty-compile-set`: 0 recorded TUs on one side while the other has >0 TUs).
3. **Install & package parity:** Stage both builds (`make install INSTALL_ROOT=...` vs `cmake --install ... --prefix ...`) and compare normalized relative paths, `bin/` vs `lib/` placement, executable permissions, and ELF `DT_NEEDED` / `RUNPATH` (CMake strips build-tree `RPATH` on install unless `INSTALL_RPATH` is set). Run the product's existing packager against the CMake staging tree and verify non-empty resource globs. On Windows, verify runtime execution in a clean environment rather than relying solely on static recursive DLL name scans (which misreport Windows API-set virtual DLLs).
4. **Runtime & incremental rebuild checks:** Execute all 8 checks on each migrated slice:
   - clean build + binary execution matching baseline output,
   - immediate second build confirming zero unnecessary codegen reruns,
   - schema/input edit confirming consumer recompilation and updated runtime output,
   - deleting a generated header and confirming automatic regeneration without a clean build,
   - touching a `Q_OBJECT` header and confirming `AUTOMOC` recompiles and relinks,
   - installing into an empty staging prefix and inspecting relative layout,
   - running the staged binary/plugins outside the build tree,
   - executing `ctest` explicitly (compiling test targets is not running tests).

## 7. CI Presets, Native Qt 6.5+ API & Adapting `tools/qmake-migration-kit/`

### Portable `CMakePresets.json` + Host `CMakeUserPresets.json` in CI

Keep [`../CMakePresets.json`](../CMakePresets.json) portable across developer machines and CI runners, and supply workstation- or runner-specific `CMAKE_PREFIX_PATH` / `Qt6_DIR` and job limits through git-ignored `CMakeUserPresets.json` (or environment variables):

```sh
# On Windows runners, initialize vcvars64.bat before invoking Ninja presets.
cmake --preset agent-release
cmake --build --preset agent-release --verbose
cmake --install out/build/agent-release --prefix out/install/agent-release
ctest --preset agent-release --output-on-failure
```

Verify in CI logs that target build, test, and packaging stages actually executed for the expected commit and preset — never accept a pipeline run where conditional parameters skipped the validation stages.

### Converging on Native Qt 6.5+ & Scoped CMake 3.25+ Targets

During Stage 1 and Stage 3 dual-building, `qmig map --qt dual` emits `find_package(QT NAMES Qt6 Qt5 REQUIRED ...)` and `Qt::*` targets so one build description compiles against both Qt 5.15 and Qt 6. Once Qt 5 is retired, switch to native Qt 6.5+ CMake commands combined with this template's `PRIVATE` warning/sanitizer helpers ([`../cmake/add_project_target.cmake`](../cmake/add_project_target.cmake)):

```cmake
cmake_minimum_required(VERSION 3.25)
cmake_policy(SET CMP0141 NEW)

project(my_qt6_app VERSION 1.0.0 LANGUAGES CXX)

find_package(Qt6 6.5 REQUIRED COMPONENTS Core Widgets Quick)
qt_standard_project_setup(REQUIRES 6.5)

qt_add_library(app_core STATIC
    src/session_model.cpp
    include/app/session_model.hpp
)
target_compile_features(app_core PUBLIC cxx_std_20)
target_include_directories(app_core
    PUBLIC
        $<BUILD_INTERFACE:${CMAKE_CURRENT_SOURCE_DIR}/include>
        $<INSTALL_INTERFACE:${CMAKE_INSTALL_INCLUDEDIR}>
)
target_link_libraries(app_core PUBLIC Qt6::Core)
cpp_template_configure_target(app_core)

qt_add_executable(my_qt6_app apps/main.cpp)
qt_add_qml_module(my_qt6_app
    URI App.UI
    QML_FILES qml/Main.qml
)
target_link_libraries(my_qt6_app PRIVATE app_core Qt6::Widgets Qt6::Quick)
cpp_template_configure_target(my_qt6_app)
```

### Adapting & Orchestrating `tools/qmake-migration-kit/`

[`../tools/qmake-migration-kit/`](../tools/qmake-migration-kit/README.md) provides customizable building blocks (`qmig.py`, `export_model.py`, `diff_models.py`, `map_to_cmake.py`) rather than a closed black box:

```sh
# 1. Initialize workflow.json (detects Qt 6 automatically if --qmake points to Qt 6)
python3 tools/qmake-migration-kit/qmig.py init \
  --source-root /path/to/qt-repo \
  --qmake /path/to/Qt/5.15.2/gcc_64/bin/qmake

# 2. Customize workflow.local.json (host paths), adapter.json (libs/tools/installPaths),
#    and policy.json (documented accepted differences such as define.ndebug).

# 3. Run export -> lint -> qt6 -> map -> capture-qmake -> capture-cmake -> compare
python3 tools/qmake-migration-kit/qmig.py run -p qt5-release
```

When adapting the scripts to a custom repository:

- **`adapter.json`:** Map external `-lfoo` flags to `IMPORTED` targets (`"libs"`), map custom generator tokens to CMake targets/variables (`"tools"`), declare `find_package(...)` calls (`"findPackages"`), rewrite legacy staging prefixes (`"installPaths"`), and opt into `"matchQmakeDefaults": true` if you want CMake `Release` drafts to omit `NDEBUG` during Stage 1 parity.
- **`policy.json`:** Record intentional flag or define differences with a mandatory `"reason"` so CI `compare` gates fail only on unreviewed regressions.
- **Extending `qmigrate/`:** Add project-specific custom-compiler patterns in `qmigrate/mapper.py` or extra probed `qmake` variables via `--qmake-arg 'MIGRATION_EXTRA_VARS+=MY_SCHEMA_FILES'` instead of hand-editing generated CMake drafts.

Run the Qt-free unit test suite and optional end-to-end Qt verification scripts from the repository root:

```sh
python3 -m unittest discover -s tools/qmake-migration-kit/tests -v
python3 tools/qmake-migration-kit/verify_demo.py --qmake /path/to/qt5/bin/qmake
python3 tools/qmake-migration-kit/verify_workflow.py \
  --qt5-qmake /path/to/qt5/bin/qmake \
  --qt6-qmake /path/to/qt6/bin/qmake
```

See [`../tools/qmake-migration-kit/README.md`](../tools/qmake-migration-kit/README.md) and [`../tools/qmake-migration-kit/KNOWN_GAPS.md`](../tools/qmake-migration-kit/KNOWN_GAPS.md) for full CLI reference and known platform limits.
